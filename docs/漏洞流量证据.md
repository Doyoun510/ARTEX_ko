# 취약점의 다중 트래픽 증거

취약점 상세의 '연관 트래픽'은 여러 페이지에 걸친 다중 선택, 용도와 설명, 정렬 및 바인딩 해제를 지원합니다. 트래픽 페이지에서도 여러 기록을 선택해 기존 취약점 하나에 한 번에 연관할 수 있습니다. 작업에서 상속한 취약점 증거는 읽기 전용이며, 수정하려면 출처 작업으로 이동해야 합니다.

시스템 설정의 'Agent 트래픽 자동 연결'은 기본적으로 꺼져 있으며, 조회·수정 인터페이스는 `/api/settings`의 `agent_traffic_binding`입니다. 켜면 요청/응답 조회, 도구 호출 및 프롬프트로 인한 Token 소비가 늘어납니다. 다음 라운드의 Agent부터 새 설정을 사용합니다. 끄면 자동 바인딩 파라미터와 누락된 바인딩을 추가하는 도구를 숨기고, 자동 바인딩 안내를 추가하지 않으며, 이미 실행 중인 세션이 새로 제출하는 자동 바인딩도 거부합니다. 수동 바인딩, 트래픽 캡처, 저장된 증거의 조회·내보내기에는 영향을 주지 않습니다.

켜면 기본 흐름은 '발견 등록 → 보고서 Agent 자동 트리거 → 트래픽 대조 및 바인딩 → 최신 증거 버전에 맞춰 보고서 작성'입니다. 보고자는 `evidence`에 검증 명령, 핵심 출력, 기존 실제 트래픽 ID와 용도를 남깁니다. 보고서 Agent는 취약점 상세와 실행 기록을 함께 살펴 `traffic_search` / `traffic_get`으로 확인한 뒤 `bind_finding_traffic`을 호출하고, 최신 `version`을 읽어 보고서를 저장합니다. 설정을 끄면 보고서 Agent에 원본 트래픽 검색/조회 도구를 추가로 제공하지 않고 자동 바인딩도 하지 않습니다. 수동으로 바인딩한 스냅샷을 읽고 보고서를 생성하는 것은 여전히 가능합니다.

기존 호출자와 호환됩니다: `report_finding`의 `traffic_refs` / `evidence_hint_id`로 명시적인 즉시 바인딩을 계속 수행할 수 있습니다. 바인딩은 선택 사항입니다. TCP 등 비 HTTP 취약점이거나, 수집하지 않았거나 정확한 기록을 찾을 수 없으면 참조를 생략해도 정상적으로 보고하고 보고서를 작성할 수 있습니다. 명령 출력, 로그 등 검증 가능한 다른 증거를 남기고 바인딩하지 않은 이유를 설명하는 것을 권고하며, 새 필수 필드를 추가하지 않습니다. 제출한 ID는 모두 유효하고 본문이 완전해야 합니다. 한 건이라도 실패하면 이번 바인딩 동작을 롤백합니다. 보고와 함께 명시적으로 바인딩하다 실패하면 보고 전체를 롤백합니다. 같은 스냅샷을 중복 추가해도 바인딩을 늘리거나 설명을 덮어쓰지 않습니다.

## Agent 번호와 보고서 버전

`report_finding`에 선택 파라미터를 추가했으며, 배열 순서가 초기 증거 순서입니다:

```json
{
  "traffic_refs": [
    {"traffic_id": "真实流量ID", "role": "baseline", "note": "正常账户请求"},
    {"traffic_id": "另一个真实流量ID", "role": "proof", "note": "复现请求"}
  ]
}
```

용도는 `baseline`(정상 대조), `proof`(취약점 입증), `verification`(추가 검증), `supporting`(보조 증거, 기본값)입니다. 먼저 `traffic_search` / `traffic_get`으로 실제 기록을 대조합니다. 도메인과 시간은 후보 선별에만 사용하며 작업 귀속을 추정하지 않습니다.

프롬프트는 [CyberStrikeAI의 취약점 보고 도구 안내](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)를 참고하며, 이 프로젝트의 선택적 바인딩 규약을 반영하고 패킷이 없는 이유를 필수로 검사하는 검증은 도입하지 않습니다. ID를 추측해서는 안 되며, 패킷을 보충하기 위해서만 중복 탐지해서도 안 됩니다.

반환 첫 줄은 여전히 `finding recorded: <探索节点 ID>`입니다. 이어지는 JSON은 독립 취약점 기록 `finding_id`, 탐색 노드 `finding_node_id` 및 바인딩 요약을 제공합니다.

- `get_finding_traffic(finding_id)`는 **독립 취약점 기록 ID**를 사용하며, 순서가 있는 목록과 `version`을 반환합니다. `binding_id`, `side=request|response`, `offset`, `length`를 전달하면 구간별로 읽을 수 있고, 각 구간은 최대 8192바이트입니다.
- `update_finding_report`의 `finding_id`는 **계속 탐색 노드 ID를 사용합니다**. 새로 추가한 `evidence_version`에는 실제로 읽은 버전을 넣습니다. 생성 중 증거가 바뀌면 이전 버전으로 쓰는 것을 거부하므로, 반드시 다시 읽고 생성해야 합니다.
- 이전 보고서 호출에서 버전을 전달하지 않으면 기존 트래픽 증거를 포괄한다고 주장하지 않습니다. 바인딩, 설명, 용도 또는 정렬이 바뀌면 기존 보고서에 업데이트가 필요하다는 안내를 표시합니다.

자동 바인딩을 켜면 `add_hint` / `add_task_hint`에서 단일 힌트 또는 일괄 `hints`의 각 요소에 `traffic_refs`를 저장할 수 있습니다. Planner가 대신 보고할 때는 `evidence_hint_id`를 전달해 이 작업의 해당 힌트에 있는 참조를 명확히 선택할 수 있으며, 상속한 힌트를 참조할 수는 없습니다. 시스템은 도메인, 시간 또는 방문 기록으로 바인딩을 추측하지 않습니다. 제출에 실패하면 취약점을 일부만 생성하거나 보고서를 미리 트리거하지 않습니다.

기존 취약점에 바인딩이 누락된 경우 `bind_finding_traffic(finding_id, traffic_refs)`로 추가 바인딩할 수 있으며, 중복 등록할 필요는 없습니다. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail`은 명확한 `finding_id`와 `finding_node_id`를 반환합니다. 기존 `id`는 탐색 노드 의미를 유지합니다.

시작 시에는 이전 도구 schema에 선택 속성만 추가하고, 원래의 기본 트래픽 도구 바인딩을 보고서 Agent까지 확장합니다. 누락된 바인딩을 추가하는 도구는 기본적으로 보고서 Agent에 제공합니다. 사용자 지정 바인딩 목록, 프롬프트, 설명 및 활성화 상태는 보존합니다. 최종 도구 조립 뒤에 안내를 공통으로 추가합니다: 보고 역할은 기존 증거를 인계하고, 보고서 Agent는 대조·바인딩·보고서 작성을 담당합니다. 플랫폼 대화에 작업 컨텍스트가 없으면 구조화된 힌트로 작업 Agent에 인계해야 하며, 직접 보고하지 않습니다. 작업 완료 판정 전에는 기존 증거부터 인계해야 합니다. 패킷이 없을 때는 대기를 강제하지 않습니다. 실패한 `report_finding`은 보고서 Agent를 트리거하지 않습니다.

## API

기본 경로: `/api/exploration/findings/{finding_id}/traffic`, 독립 취약점 ID를 사용합니다. 기존 인증을 따르며, `context_task`로 작업 조회 가능 여부와 상속 읽기 전용을 검사합니다.

| 메서드 / 상대 경로 | 요청 / 반환 |
| --- | --- |
| `GET` | 순서가 있는 요약, 증거 버전, 보고서가 사용한 버전 |
| `POST` | `{"traffic_refs":[...]}` 일괄 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"说明"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`, 반드시 전체 목록이어야 합니다 |
| `GET /{binding_id}` | 스냅샷 메타데이터와 범위가 제한된 본문 미리보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`; `download=1`은 원본 바이트 전체를 다운로드합니다 |

버전/정렬 집합 충돌과 아카이브 중 쓰기는 `409`를 반환합니다. 상속한 증거에 쓰면 `403`, 바인딩이 없거나 해당 취약점에 속하지 않으면 `404`를 반환합니다. 트래픽/첨부파일 조회와 검증에 실패하면 명확한 오류를 반환합니다.

## 저장과 마이그레이션

시작 시 PostgreSQL에 멱등 마이그레이션을 수행합니다: `traffic_evidence_snapshots`, `finding_traffic_bindings` 및 `findings.evidence_version` / `report_evidence_version`(기본값 0)을 추가합니다. 과거 텍스트로 누락된 바인딩을 추측해 추가하지 않습니다.

스냅샷은 원본 트래픽 ID, 수집 시간, URL, 메서드, 상태, 요청/응답 헤더, 본문 길이 및 SHA-256을 저장합니다. 본문은 해시별로 `<data>/evidence/blobs/<前两位>/<hash>.bin`에 저장하며, 정리 가능한 `data/traffic`과 분리되고 여러 취약점이 스냅샷/본문을 공유할 수 있습니다. 스냅샷은 내용 업데이트 인터페이스를 제공하지 않으며, 검증 결과가 일치하지 않으면 조회와 내보내기에 실패합니다.

원본 트래픽의 쓰기 잠금 아래에서 대용량 본문 blob과 이전 디렉터리 기록을 포함한 본문 전체를 읽습니다. 먼저 파일을 영구 저장하고 검증한 뒤, 단일 PostgreSQL 트랜잭션으로 탐색 노드, 의도 관계, 취약점, 스냅샷 및 바인딩을 기록합니다. 트랜잭션을 커밋한 뒤에만 planner에게 알립니다. 실패하면 참조되지 않는 파일이 남을 수 있지만, 업무 기록을 일부만 생성하지는 않습니다.

PostgreSQL advisory lock `7337741004`로 증거 파일과 SQL 참조를 조율합니다. 작업 행 잠금은 아카이브 대기열에 들어간 뒤의 증거 수정을 금지합니다. 복원 시 본문 설치부터 메타데이터 커밋까지 전 과정에서 증거 잠금을 유지합니다. 취약점을 삭제하면 바인딩을 연쇄 제거합니다.

정리 프로세스는 매시간 실행하며, 참조가 없고 진행 중인 동작에 속하지 않는 내용만 최소 24시간이 지난 뒤 회수합니다. 일반 트래픽 정리는 증거 디렉터리에 영향을 주지 않습니다. 활성 데이터를 백업할 때는 PostgreSQL과 `data/evidence`를 함께 백업합니다.

## 내보내기와 아카이브

Markdown은 순서가 있는 증거 목록과 버전을 포함합니다. JSON은 메타데이터를 포함하고, CSV에는 개수와 바인딩 ID를 추가합니다. `md-zip`은 취약점 Markdown을 보존하고 다음을 제공합니다:

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown은 상대 링크로 메시지를 참조합니다. 다운로드를 전송하기 전에 첨부파일 복사, 해시 검증, 압축, 디스크 동기화 및 모든 ZIP 항목의 CRC 읽기 검증을 완료합니다. 누락/손상이 있으면 다운로드 전체가 실패합니다. 전체 첨부파일은 원본 바이너리 바이트를 보존합니다.

아카이브 v3는 취약점 바인딩 관계에 따라 스냅샷과 본문을 수집하며, 원본 트래픽이나 도메인에 의존하지 않습니다. 패키지 검증을 완료한 뒤에만 활성 데이터를 정리하며, 공유 증거는 계속 보존합니다. 복원 시 먼저 본문을 검증·설치한 뒤 트랜잭션으로 메타데이터와 바인딩을 복원하며, 실패 시 재시도를 지원합니다. v1/v2는 계속 복원할 수 있고 누락된 새 필드는 명시적으로 0을 채웁니다.

## 검증과 경계

각 테스트 패키지에 새로 만든 별도의 PostgreSQL 테스트 DB를 설정하고 `ARTEX_PG_DSN`으로 지정해, 남아 있는 작업/모델 fixture가 백그라운드 실행을 트리거하지 않도록 합니다. 관련 패키지의 전체 테스트를 실행하고 설정 누락 때문에 건너뛰는 항목이 없는지 확인합니다:

```sh
# 每个包运行前将 ARTEX_PG_DSN 设为对应的独立测试库；显式配置失败必须报错。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

프런트엔드 검증에는 `npx tsc --noEmit`, 영향을 받는 파일의 Biome 검사, Webpack 빌드 및 `NEXT_EXPORT=1` 정적 내보내기가 포함됩니다. 별도의 캐시 디렉터리를 사용해 실행 중인 개발 서비스를 덮어쓰지 않도록 합니다.

로컬 종단 간 검증에는 별도 포트, 통제된 HTTP / 도메인 HTTPS 대상 및 임시 데이터 디렉터리를 사용하며, 두 바인딩 진입점, 여러 페이지에 걸친 선택, 정렬/설명, 오류 안내, 상속 읽기 전용, 다운로드와 원본 트래픽 삭제 후 내보내기, 아카이브, 활성 본문 데이터 회수, 복원 및 해시 검증을 포함합니다.

첫 버전은 전역 증거 조율 잠금을 사용하며, 대량 바인딩/내보내기 또는 느린 첨부파일 다운로드 중에는 다른 증거 동작이 대기할 수 있습니다. 레코딩 기록이나 완전한 본문이 없으면 증거를 만들어 보충할 수 없습니다. 이 기능은 캡처 설정을 바꾸지 않으며 HTTPS로 IP에 직접 접속할 때의 인증서 문제도 처리하지 않습니다.
